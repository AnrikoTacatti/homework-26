## 1. Декомпозиция

_6–8 сервисов с описанием ответственности._
| Сервис | Ответственность |
|--------|-----------------|
| **API Gateway** | Единая точка входа в систему. Принимает запросы от клиентов, выполняет маршрутизацию, проверку JWT-токенов, rate limiting и перенаправляет запросы в соответствующие сервисы. |
| **Authorization Service** | Выполняет регистрацию, аутентификацию и авторизацию пользователей. Выпускает и обновляет JWT-токены, управляет ролями и правами доступа. |
| **User Service** | Управляет профилями пользователей. Хранит персональные данные, информацию о верификации (KYC), лимитах и настройках аккаунта. |
| **Wallet Service** | Управляет электронными кошельками пользователей. Хранит баланс, выполняет резервирование, списание и зачисление денежных средств. |
| **Payment Service** | Обрабатывает платежи. Создаёт платежи, координирует перевод средств между кошельками, взаимодействует с другими сервисами и публикует события после успешного завершения операции. |
| **Fraud Service** | Проверяет операции на признаки мошенничества. Анализирует сумму платежа, лимиты, частоту операций, IP-адрес, устройство пользователя и другие факторы риска. |
| **Transaction History Service** | Хранит историю всех финансовых операций. Предоставляет API для просмотра, поиска и фильтрации истории платежей. |
| **Receipt Service** | Формирует электронные чеки и квитанции после успешного проведения платежа. Предоставляет возможность скачать чек или отправить его пользователю по электронной почте. |
| **Notification Service** | Отправляет пользователям Email, SMS и Push-уведомления о статусе платежей и других событиях системы. |
| **Analytics Service** | Собирает статистику и формирует отчёты по количеству платежей, обороту средств, активности пользователей и другим бизнес-показателям. |
| **Audit Service** | Ведёт журнал всех финансовых и административных действий. Используется для аудита, расследования инцидентов и выполнения требований регуляторов. |

## 2. Протоколы

_REST / gRPC / GraphQL / events — где и почему._

| Откуда | Куда | Протокол | Назначение |
|--------|------|----------|------------|
| Client | API Gateway | REST | Внешнее API для web и мобильных клиентов. |
| API Gateway | Authorization Service | gRPC | Регистрация, аутентификация, проверка JWT-токена. |
| API Gateway | User Service | gRPC | Получение и изменение данных пользователя. |
| API Gateway | Wallet Service | gRPC | Получение информации о кошельке и балансе. |
| API Gateway | Payment Service | gRPC | Создание платежа, получение статуса платежа. |
| API Gateway | Transaction History Service | gRPC | Получение истории операций пользователя. |
| Payment Service | Wallet Service | gRPC | Проверка баланса, резервирование, списание и зачисление средств. |
| Payment Service | Fraud Service | gRPC | Проверка платежа на признаки мошенничества. |
| Payment Service | Kafka | Event (PaymentCompleted) | Публикация события после успешного выполнения платежа. |
| Kafka | Transaction History Service | Event (Pub/Sub) | Сохранение информации о выполненном платеже в историю операций. |
| Kafka | Receipt Service | Event (Pub/Sub) | Формирование электронного чека после успешного платежа. |
| Kafka | Notification Service | Event (Pub/Sub) | Отправка Email, SMS и Push-уведомлений пользователю. |
| Kafka | Analytics Service | Event (Pub/Sub) | Сбор статистики и построение аналитических отчётов. |
| Kafka | Audit Service | Event (Pub/Sub) | Запись информации о финансовой операции в журнал аудита. |

## 4. API-контракты

_3–4 ключевых API (Swagger/OpenAPI или описание)._

| Сервис | API | Метод | Назначение | Request | Response |
|--------|-----|--------|------------|---------|----------|
| **Authorization Service** | `/auth/login` | `POST` | Аутентификация пользователя и получение JWT-токена. | `{"login":"user@example.com","password":"password123"}` | `{"accessToken":"...","refreshToken":"..."}` |
| **Payment Service** | `/payments` | `POST` | Создание нового платежа между двумя кошельками. | `{"fromWalletId":"wallet-1","toWalletId":"wallet-2","amount":1000,"currency":"RUB","idempotencyKey":"123456"}` | `{"paymentId":"pay-123","status":"PROCESSING"}` |
| **Wallet Service** | `/wallets/{walletId}` | `GET` | Получение текущего баланса кошелька. | `walletId` | `{"walletId":"wallet-1","balance":25000,"currency":"RUB"}` |
| **Transaction History Service** | `/transactions` | `GET` | Получение истории финансовых операций пользователя. | `userId`, `page`, `size` | `[{"transactionId":"tr-101","paymentId":"pay-123","amount":1000,"status":"SUCCESS"}]` |

## 5. Асинхронность

_Где применяется и почему._


| Тип взаимодействия | Где применяется | Почему |
|--------------------|-----------------|---------|
| **Синхронное (REST)** | Client → API Gateway | Клиент ожидает результат выполнения операции. |
| **Синхронное (gRPC)** | API Gateway → Payment Service | Необходимо дождаться результата обработки платежа. |
| **Синхронное (gRPC)** | Payment Service → Wallet Service | Перед выполнением платежа необходимо проверить баланс и выполнить списание средств. |
| **Синхронное (gRPC)** | Payment Service → Fraud Service | До проведения платежа требуется проверить операцию на признаки мошенничества. |
| **Асинхронное (Kafka Events)** | Payment Service → Transaction History Service | История операций обновляется после завершения платежа и не влияет на скорость ответа клиенту. |
| **Асинхронное (Kafka Events)** | Payment Service → Receipt Service | Формирование электронного чека выполняется в фоновом режиме. |
| **Асинхронное (Kafka Events)** | Payment Service → Notification Service | Отправка Email, SMS и Push-уведомлений не должна задерживать выполнение платежа. |
| **Асинхронное (Kafka Events)** | Payment Service → Analytics Service | Сбор статистики выполняется независимо от основной бизнес-операции. |
| **Асинхронное (Kafka Events)** | Payment Service → Audit Service | Запись информации о финансовой операции в журнал аудита выполняется после публикации события. |


## 6. Паттерны

_Saga, CQRS и т.д. — обоснование._

| Паттерн | Где на схеме | Где применяется | Обоснование |
|----------|--------------|-----------------|-------------|
| **Saga (Orchestration)** | `Payment Service → Wallet Service → Fraud Service → Wallet Service` | Payment Service | `Payment Service` выступает оркестратором процесса оплаты: последовательно вызывает сервисы, контролирует выполнение шагов и при ошибке выполняет компенсирующие действия (например, отмену резервирования средств). |
| **CQRS** | `Payment Service → Kafka → Transaction History Service` (запись) и `Client → API Gateway → Transaction History Service` (чтение) | Transaction History Service | Запись истории платежей выполняется после получения события `PaymentCompleted`, а чтение осуществляется через отдельный API `GET /transactions`. Это разделяет операции изменения и чтения данных, упрощает масштабирование и оптимизацию сервиса. |
| **Outbox Pattern** | `Payment Service → Outbox → Kafka` *(не показан на схеме)* | Payment Service | Перед публикацией события в Kafka оно сначала сохраняется в таблице **Outbox**. Это предотвращает потерю события при недоступности Kafka. |
| **Idempotency** | `Client → API Gateway → Payment Service` | Payment Service (`POST /payments`) | Каждый запрос содержит `Idempotency-Key`. При повторном запросе с тем же ключом новый платёж не создаётся, а возвращается результат ранее выполненной операции. |
| **Publish/Subscribe (Pub/Sub)** | `Payment Service → Kafka → History / Receipt / Notification / Analytics / Audit` | Kafka | После успешного завершения платежа `Payment Service` публикует событие `PaymentCompleted`, а подписанные сервисы (`Transaction History Service`, `Receipt Service`, `Notification Service`, `Analytics Service` и `Audit Service`) независимо получают и обрабатывают его. |
